# Dafne Architecture Phases

<2026-07-18 to 2026-07-26 — branch master — sessions 4d874e, 3219b8, 436d23, cc6b0e, d2f497, d86a84>

## Summary
A full `dafne_simulation/` sandbox was built to validate node inheritance (grove, language, spanish) using symlinked parents and per-node `DAFNE.md` manifests, settling several architectural decisions: the node/grove split, removal of `parents:[]` from manifests in favor of delegating to git submodules, and reserving `.private/` for node-private scripts. Three open decision points from that build — freeze vocabulary and union-up-the-tree behavior, pin-vs-range versioning (which was later settled toward version pins plus assisted-update UX, deferring a range field as future-additive), and the production `groves/` migration — were tracked forward through subsequent sessions alongside a UX topology sketch of three interaction modes (direct grove opening, git-model launcher, managed library) documented in `interaction_north_star.md`. Phase 0 concluded with golden snapshots committed and verified against real production content, confirming the SessionStart-hook spike unblocks the runtime, leaving Phase 1 — a standalone DAFNE engine repo under `plugins/dafne`, absorbing `context-compiler`, and implementing manifest reading with requires-union — queued but not started, with the connection protocol for standalone groves (see [[grove-inheritance-connection-protocol-decision]]) remaining the main unresolved point. A related governance question surfaced: whether architect/builder modes belong in the repo as separate groves, as runtime-orchestrator agent concepts, or folded into an existing grove — DAFNE's structural rules make them look grove-shaped (they have registered mem-banks) while `product-vision.md` positions agent definitions in the runtime, not in groves, complicated further by architect and builder currently sharing one `meta` mem-bank; this was filed as issue #19. Two further investigation issues (#29 audio-tts for pronunciation generation, #30 intake for Zotero/Readwise-style source tooling) were opened for potential new `requires:` plugin categories, both referencing the prerequisite plugin-binding mechanism (issue #17, plugin dependency resolution for turning a grove's `requires: anki` into an installed, activated plugin) and following a zero-instance investigation-first discipline, validated in part by the social-dynamics grove (see [[social-dynamics-grove-design]]) proving the tool layer is optional and additive rather than foundational.
